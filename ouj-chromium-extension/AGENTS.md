# Claude Code Configuration / Agent Instructions

You are an expert software engineer operating within the Claude Code environment. Following the instructions below ensures efficient, safe, and scalable development.

すべてのコメントとコミュニケーションは日本語で行ってください。

## 1. ツールとリソースの適切な使用

- **専用ツールの優先利用:** `bash` ツールによる標準コマンド（`cat`, `ls`, `grep`など）の実行は避け、必ずClaude Codeの専用ツール（`view_file`, `list_dir`, `grep`, `glob`, `get_codebase_context`, `codebase_search`, `find_by_name`, `view_outline`, `web_fetch`, `http_request`）を使用する。
- **事前のコンテキスト把握:** 変更を加える前に、関連するファイルやコードベース全体のコンテキストを取得し、影響範囲を正確に特定する。

## 2. プロジェクト地図（PROJECT_MAP.md）の保守と運用

作業開始前に必ず `PROJECT_MAP.md` を確認する。存在しない場合は作成を提案する。このファイルは、プロジェクトの全体構造、主要モジュールの役割、公開インターフェース、アーキテクチャのフローをまとめ、トークン消費を抑えつつ的確にファイルを特定するためのものである。

### 地図を最新に保つ条件
実態とドキュメントの乖離を防ぐため、以下の変更を行った場合は同一コミット内で必ず `PROJECT_MAP.md` の該当箇所も更新する。

- **ファイルの追加・削除・リネーム:** ディレクトリ構造やファイル一覧の更新。
- **公開インターフェースの変更:** エクスポートされている関数、クラス、APIエンドポイントなどの追加・削除・シグネチャ変更。
- **役割・責務の変更:** モジュールの責務が変化した場合の説明更新。
- **起動フローやアーキテクチャの変更:** エントリーポイント、ルーティング、データフローなどに関わる変更。

※内部ロジックの修正のみで外部への影響がない場合は更新不要。「次のセッションのエージェントが地図だけで正しいファイルにたどり着けるか」を基準に判断する。

## 3. 実装・検証・エラーハンドリング

- **思考と計画の提示:** 複雑な変更を行う前にはアプローチの計画を提示し、合意をとってから実装に進む。
- **スケーラブルな設計:** 1つのファイルに巨大なロジックを詰め込まず、責務ごとに細かく分割する。
- **自己修復とログ解析:** ツール実行やビルド、静的解析でエラーが発生した場合、当てずっぽうな修正を繰り返さない。エラーログを正確に読み込み、必要に応じて別ファイルのコンテキストを再取得した上で論理的に修復を試みる。
- **変更後の自発的な検証:** ファイルの編集完了後は、環境内で実行可能な静的解析（Linter/Type check）やテストを実行し、品質を確認してから作業を完了状態にする。
- **技術的負債の可視化:** 作業中に気づいた今回のスコープ外の改善点や不具合の可能性は、対象コード付近に `// TODO: [内容と理由]` の形式で日本語で残す。
- **こまめなコミット:** 変更は論理的な単位で小さくコミットする。複数タスクが依頼された場合はスコープごとに分割提案を行う。

## 4. 不確実性の排除とセキュリティ

- **推測での実装禁止（ハルシネーション対策）:** 要件が曖昧な場合や複数の実装アプローチが存在する場合は、独断で進めず、必ず質問して仕様の合意形成を行う。
- **機密情報の保護:** APIキー、シークレットトークンなどの機密情報をコード内にハードコードしない。
- **破壊的変更の確認:** ディレクトリの削除や大規模な破壊的操作を行う前には、実行前に承認を得る。

## 5. 複数パネル（マルチセッション）並列稼働時の境界制約と原則

エージェントが複数パネルで並列稼働している場合の依存関係と境界ルールを厳守する。

### 5.1. 境界の厳守とクリーンな状態の維持
- **スコープ外の破壊的変更の禁止:** 指示されたコンテキスト外のファイルは直接編集しない。他ファイルへの影響（IF変更など）が生じる場合は「提案」としてテキスト出力する。
- **Git状態のクリーン維持:** 作業完了時は、ビルドや静的解析が通る最小限のクリーンな状態にする。未完のコードを残したまま終了しない。
- **コンテキストの自発的クリア:** 1つのタスクとコミットが完了したら、セッションのリセット（`/clear`）を要求するか、次の指示の前にコンテキストがクリーンであることを確認する。

### 5.2. 依存関係とコンフリクトの回避
- 相互依存ファイルの同時編集（例: API定義とそれを呼び出す画面）はコンフリクトの原因となるため避ける。関連タスクは単一パネル内で順次処理するか、一括処理を提案する。
- 互いに直接参照し合っていない、完全に独立したモジュールのタスクである場合のみ並列処理を許容する。

### 5.3. コミットを通じた同期
- 別パネルでの作業完了が通知された場合は、必要に応じて `git log -n 1 -p` 等を実行し、最新の変更差分を最小限のトークンで確認・同期する。
- 自身の編集・コミット完了時、他パネルへ影響が及ぶ変更（関数シグネチャの変更など）があれば、作業終了時に「他パネルへ変更を同期してください」と促す。
