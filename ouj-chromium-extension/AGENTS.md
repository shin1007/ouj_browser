# Claude Code Configuration

Always use specific read-only tools (`view_file`, `list_dir`, `grep`, `glob`, `get_codebase_context`, `codebase_search`, `find_by_name`, `view_outline`, `web_fetch`, `http_request` ) instead of running commands like `cat`, `ls`, `grep` via the `bash` tool.

コメントはすべて日本語で行ってください。

## まず読むもの: プロジェクト地図

作業前に [PROJECT_MAP.md](PROJECT_MAP.md) を読んでください。全ファイルの役割・公開IF（`window.*`）・ロード順・ページ別起動フローをまとめてあり、コードベース全体をgrepせずに担当ファイルを特定できます（トークン節約が目的）。

### 地図を最新に保つ

地図が実態とずれると、それを信じた次のセッションが誤ったファイルを触り、かえってトークンと手戻りが増えます。以下の変更をしたら、同じコミット内で [PROJECT_MAP.md](PROJECT_MAP.md) の該当箇所も必ず更新してください。

- **ファイルの追加・削除・リネーム** … 一覧表の行と、`manifest.json` のロード順に関わる記述を更新する。
- **公開IF（`window.*` 関数）の追加・削除・改名** … 該当ファイルの「主な公開IF」列を更新する。
- **ファイルの役割・責務が変わったとき** … 「役割」列を実態に合わせる。
- **content.js のページ別起動フローが変わったとき** … 末尾のフロー図を更新する。

軽微な実装変更（内部ロジックのみで役割・IF・起動フローが変わらない）では地図を触らなくてよいです。迷ったら「次のセッションがこの地図だけを見て正しいファイルにたどり着けるか」を基準に判断してください。

## 気づいたことはTODOとして残す

作業中に気づいたが今回は変更を加えなかった点は、必ずTODOコメントとして残してください。

- 対象のコード付近に `// TODO: ...`（日本語で内容を記述）を挿入する。
- 変更しなかった理由と、将来どうすべきかが分かるように書く。
- 黙って見送らず、気づいた改善点・不具合の可能性は都度TODOとして明示する。

## 今後のことを考えた編集を行う

- エージェントを並列で走らせることを前提としたファイル構成にする。不必要に大きなファイルを作らず、細かく分割する。
- 日本語でのコメントを適宜行う。
- 1回のセッションでトークンを過剰消費しないように配慮する。
- コミットはこまめに行う。複数の修正を指示された場合は、スコープごとに分けて指示を出しなおすことも提案してよい。

## 複数パネル並列稼働時の境界制約

あなたは複数のセッションで並列稼働しているエージェントの1人です。以下の境界を厳守してください。

- **スコープ外の破壊的変更の禁止:** 指示されたファイル以外のコードを直接書き換えないでください。他ファイルへの影響（IFの変更など）が生じる場合は、編集せず「提案」としてテキストで出力してください。
- **Git状態のクリーン維持:** 編集完了時は、ビルドやテストが通る最小限のクリーンな状態でコードを出力（または適用）してください。未完のコードをファイルに残したままツールを終了しないでください。
- **コンテキストの自発的クリア:** 1つのファイルの修正とコミットが完了したら、ユーザーにセッションのリセット（`/clear`）を要求するか、次の指示を受ける前にコンテキストがクリーンであることを確認してください。

## 複数パネル（マルチセッション）並列稼働時の原則

人間（ユーザー）が複数のパネルを開いてあなた（エージェント）を並列稼働させている場合、以下の依存関係と境界のルールを厳守し、必要に応じてユーザーに運用の提案を行ってください。

### 1. ファイルまたぎの依存関係における制御
相互に直接参照し合っている、または依存関係があるファイルの同時編集は、コンフリクトとトークン過剰消費の原因になります。

- **NG（コンフリクト対象）：** パネルAで「APIの関数定義」を修正し、同時にパネルBで「そのAPIを呼び出すUI画面」を修正するような運用。
- **OK（推奨される安全な運用）：** 依存関係がある場合は、単一のパネル（セッション）内で順番に指示を受けるか、関係するファイルをすべて1つのパネルに `@メンション` で読み込ませて一括で処理する。
- **並列化してよいケース：** `src/components/Button.tsx` と `src/utils/format.ts` のように、互いに直接参照し合っていない完全に独立したタスク・ファイルの場合のみ、別パネルでの並列処理を受け入れる。

※もしユーザーから「依存関係で衝突しそうな別パネル側の修正」を同時に進めるよう指示された場合は、上記の原則を元に、単一セッションへの統合や順番の変更を提案してください。

### 2. コミットメッセージを用いたコンテキストの同期
別パネルで進行した修正内容を、あなたのセッションはリアルタイムで関知できません。他パネルでの変更内容（特にインターフェースや依存先への影響）を同期する必要がある場合は、以下の手段をとってください。

- ユーザーから他パネルでの修正完了を伝えられた場合、必要に応じて `git log -n 1 -p` 等を実行し、最新のコミットハッシュや変更差分を最小限のトークンで確認・同期する。
- あなた自身が編集・コミットを完了した際、他パネルへ影響が及びそうな変更（関数シグネチャの変更など）があれば、ユーザーに対して「他パネルへの通知・同期」を促す文言を添える。
